# World Impulsive Indicator — 拡張 User Story Map

## 1. プロダクト概要

### 1.1 As-Is：オリジナル版

世界に対する人々の衝動を、感情表明と集計によって可視化するWebアプリケーション。

対象となる衝動は以下の3種類。

- 一揆したい
- 国外脱出したい
- 祭りたい

ユーザーは同じ衝動を繰り返し表明でき、その結果が他のユーザーの表明と集計される。

感情表明そのものに娯楽性があり、ランダムな演出やレア演出を楽しめる。

正確な世論調査ではなく、集合的な衝動を可視化する作品である。

**オリジナル版は独立した作品として維持する。**

既存仕様は [オリジナル版USM](./user-story-map.md) を参照する。

### 1.2 ToBe：感情表明プラットフォーム

**人々が任意の評価対象に対して、ポジティブ・ネガティブな感情を何度でも表明し、その集積と変化を可視化できるプラットフォーム。**

ユーザーの利用動機は、評価対象に対して感情を表明することで、対象に何らかの影響を与えたいという欲求にある。

例えば、

- 好きな漫画やアプリを応援したい
- 気に入らない商品やサービスに不満を表明したい
- 自分が暮らす街に愛着や不満を表明したい
- ライブやイベントに対して感情を送りたい

といった行動を想定する。

ユーザーは評価対象のカテゴリを選択し、具体的な対象名を自由記述で入力する。

評価対象ごとに独立したページが作成され、誰でもその対象に感情を表明できる。

### 1.3 プロダクトの基本原則

1. **表明を重視する**：正確な評価を収集することよりも、感情を表明する体験を重視する。
2. **繰り返し表明できる**：一人一票に限定せず、既存の投票ルールの範囲で繰り返し表明できる。
3. **感情を直感的に表現する**：文章によるレビューではなく、具体的な行動を想起できる衝動表現を使用する。
4. **集積を可視化する**：他のユーザーによる表明も集計され、対象の状態に反映される。
5. **娯楽性を維持する**：既存の演出・レア演出の仕組みを継承する。
6. **レア演出を調整できる**：レア演出のON/OFFを切り替えられる。
7. **評価対象を細分化しない**：一つの評価対象を、個別の話題や要素に分解する仕組みは設けない。
8. **集計の意味を明確にする**：表明数は人数や支持率を意味しない。
9. **対象への影響を保証しない**：感情を届ける機会を提供するが、対象側の対応や改善を保証しない。

## 3. User Story Map

### Backbone：ユーザーの主要活動

1. 体験するモードを選ぶ
2. 感情を向ける対象を決める
3. 衝動を選んで表明する
4. 感情の集積と変化を見る
5. 再訪・共有する

### ストーリーマップ

| Activity | Step 1：函南町モード | ToBe：汎用プラットフォーム |
|---|---|---|
| 1. モードを選ぶ | オリジナル版 / 函南町版を切り替える | オリジナル版 / 評価プラットフォームを切り替える |
| 2. 対象を決める | 静岡県函南町に固定 | カテゴリを選び、対象名を自由入力する |
| 3. 感情を表明する | 函南町専用の3つの衝動を表明する | 対象に対して用意された衝動を表明する |
| 4. 結果を見る | 函南町専用の集計・変化を見る | 対象ごとの集計・変化を見る |
| 5. 再訪・共有する | モードを再訪し、更新された状態を見る | 対象ページに再訪し、URLを共有する |

# 4. Step 1：函南町モードの追加

## 4.1 目的

オリジナル版の感情表明・集計・可視化の仕組みを、世界以外の特定対象にも適用できることを検証する。

対象は**静岡県函南町**に固定する。

将来の汎用プラットフォーム化を見据えるが、Step 1では汎用的な対象ページ生成機能を実装しない。

UIモックは作成済みとし、本USMでは実際の機能要件を定義する。

## 4.2 想定ユーザー

主に函南町に暮らす人。

自分が暮らす町に対する愛着、不満、離れたい気持ちなどを表明したい人を想定する。

観光客や来訪者向けの評価体験は、Step 1では考慮しない。

## 4.3 函南町モードの3つの衝動

| 衝動 | 意味 |
|---|---|
| 一揆したい | 不満・変革。この町の現状を変えたい |
| 荷物をまとめたい | 離脱・転出。この町から引っ越したい |
| 骨を埋めたい | 愛着・定住。この町で暮らし続けたい |

画面ではこの順序（一揆したい → 荷物をまとめたい → 骨を埋めたい）で並べる（2026-11-15 決定）。

オリジナル版とは衝動の種類を分離する。

同じ「一揆したい」という文言でも、オリジナル版と函南町版では別の集計として扱う。

## 4.4 User Stories

### Activity 1：モードを選ぶ

**S1-01：モードを切り替える**

ユーザーとして、オリジナル版と函南町版を切り替えたい。

世界と函南町のどちらに感情を表明するか選びたいから。

**Acceptance Criteria**

- オリジナル版と函南町版を切り替えられる。
- 現在のモードを識別できる。
- 切り替えたモードに対応する衝動と集計が利用できる。
- オリジナル版は従来どおり利用できる。

### Activity 2：評価対象を決める

**S1-02：函南町を評価対象として利用する**

ユーザーとして、函南町に対する感情を表明したい。

自分が暮らす町への気持ちを示したいから。

**Acceptance Criteria**

- 函南町モードの評価対象は静岡県函南町に固定されている。
- ユーザーによる対象名の入力は不要。
- 函南町以外の評価対象は作成できない。

### Activity 3：衝動を選んで表明する

**S1-03：函南町への衝動を表明する**

ユーザーとして、函南町に対して3種類の衝動から選んで表明したい。

愛着、不満、離脱願望を直感的に表現したいから。

**Acceptance Criteria**

- 「骨を埋めたい」「一揆したい」「荷物をまとめたい」の3種類を利用できる。
- それぞれの衝動を独立して集計する。
- オリジナル版と同じ基本的な投票体験を利用できる。

**S1-04：繰り返し表明する**

ユーザーとして、同じ衝動を繰り返し表明したい。

一度の操作だけでなく、感情の強さを行動で表現したいから。

**Acceptance Criteria**

- 既存の投票ルールの範囲で連続して表明できる。
- 投票上限・集計期間・寄与度調整などは既存仕様を基本的に継承する。
- 表明時の通常演出が機能する。
- 投票上限に達した場合は、既存の制限ルールに従う。

**S1-05：レア演出を切り替える**

ユーザーとして、レア演出をON/OFFしたい。

自分の好みに応じて感情表明の体験を調整したいから。

**Acceptance Criteria**

- レア演出のON/OFFを切り替えられる（設定はオリジナル版に効く）。
- ONの場合、オリジナル版でレア演出が発生し得る。
- OFFの場合、レア演出は発生しない。
- **函南町モードにはレア演出を設けない（OFF固定）**。投票ごとの演出は衝動ごとに1種類（2026-11-15 決定）。
- OFFでも通常演出と感情表明は維持される。
- ON/OFFによって投票の集計結果や寄与度は変わらない。

### Activity 4：感情の集積を見る

**S1-06：函南町への感情の集積を見る**

ユーザーとして、函南町に対して集まった衝動を見たい。

自分以外の人々が町に抱いている感情の熱量を感じたいから。

**Acceptance Criteria**

- 函南町の3種類の衝動を独立して集計する。
- 集計結果はバックエンドで管理され、複数ユーザー間で共有される。
- 集計結果が更新されると、可視化される状態にも反映される。
- オリジナル版の集計と混在しない。
- モードを切り替えても、それぞれの集計が適切に取得される。
- 表示数値は既存仕様と同様に有効投票数として扱う。

### Activity 5：再訪する

**S1-07：オリジナル版を引き続き楽しむ**

ユーザーとして、函南町モードの追加後もオリジナル版を従来どおり楽しみたい。

既存の作品としての体験を失いたくないから。

**Acceptance Criteria**

- オリジナル版の3つの衝動は変更されない。
- オリジナル版の投票・集計・可視化が維持される。
- 函南町モードの投票はオリジナル版の結果に影響しない。
- 函南町モードを追加したことで、オリジナル版に既存機能の不具合が生じない。

## 4.5 Step 1の共通要件

### 集計

- オリジナル版と函南町版の投票データを論理的に分離する。
- モードごと、衝動ごとに集計する。
- 投票上限などの制限が意図せず別モードへ影響しないようにする。
- 既存の投票・集計仕様を不必要に変更しない。
- 集計結果は支持者の人数や町民の支持率として扱わない。

### 既存機能との互換性

- オリジナル版の既存データを保持する。
- 既存の投票・集計・可視化の仕組みを可能な限り再利用する。
- 新しいモードの追加によって既存のAPI利用や画面動作を破壊しない。
- 評価対象である函南町と、投票者の位置情報は別の概念として扱う。

### モックとの関係

- 作成済みの函南町モードのモックをUI実装時の参照資料とする。
- 本USMは機能と受け入れ条件を定義する。
- 個別のデザイン仕様は本USMには含めない。
- モックに含まれる表現や挙動が本USMと矛盾する場合は、実装前に確認する。

## 4.6 Step 1で実装しないもの

- カテゴリ選択
- 評価対象の自由入力
- 評価対象ページの作成・払い出し
- 函南町以外の地域への対応
- 漫画、アプリ、会社、ライブなどへの対応
- 個別テーマや評価項目への細分化
- コメント、レビュー、星評価
- ユーザー登録・プロフィール
- 評価対象の管理者向け機能
- 正確な満足度調査・世論調査機能

## 4.7 Step 1のDefinition of Done

- [ ] S1-01：2つのモードを切り替えられる
- [ ] S1-02：函南町が固定の評価対象として利用できる
- [ ] S1-03：函南町専用の3種類の衝動を表明できる
- [ ] S1-04：既存ルールに従って繰り返し表明できる
- [ ] S1-05：レア演出のON/OFFが機能する
- [ ] S1-06：函南町専用の集計・可視化が機能する
- [ ] S1-07：オリジナル版の機能・データが維持される
- [ ] 複数ユーザー間で函南町の集計結果を共有できる
- [ ] 2つのモードの集計データが混在しない
- [ ] 主要な既存テストと追加機能のテストが通る

# 5. ToBe：感情表明プラットフォーム

## 5.1 目的

任意の評価対象に対して感情を表明できるようにし、既存の体験をさまざまな対象へ展開する。

Step 1で固定されていた函南町という評価対象を、ユーザーが自由に指定できるようにする。

## 5.2 対象カテゴリ

想定するカテゴリは以下。

- 街・地域
- 漫画・アニメ
- アプリ・ゲーム
- 会社・組織
- ライブ・イベント

カテゴリは将来的に追加できるものとする。

カテゴリごとに衝動の種類が異なる可能性はあるが、詳細は今後決定する。

## 5.3 User Stories

### Activity 1：カテゴリを選ぶ

**TB-01：カテゴリを選択する**

ユーザーとして、感情を向けたい対象のカテゴリを選びたい。

自分が評価したい対象の種類を指定するため。

**Acceptance Criteria**

- 用意されたカテゴリから選択できる。
- カテゴリに応じた評価対象を作成できる。

### Activity 2：評価対象を指定する

**TB-02：評価対象を自由入力する**

ユーザーとして、評価対象の名前を自由記述で入力したい。

自分が感情を表明したい対象を指定するため。

**Acceptance Criteria**

- カテゴリ選択後、対象名を入力できる。
- 既存の選択肢からしか対象を選べない仕組みにはしない。
- 対象内部のキャラクターや特定の話題などへ細分化する操作は設けない。

**TB-03：評価対象のページを作成する**

ユーザーとして、入力した評価対象のページを作りたい。

その対象に感情を集める場所を作るため。

**Acceptance Criteria**

- 評価対象ごとに独立したページを作成できる。
- 各ページは独立した感情集計を持つ。
- 作成したページには他のユーザーもアクセスできる。

### Activity 3：感情を表明する

**TB-04：対象への衝動を表明する**

ユーザーとして、指定した対象への感情を表明したい。

対象を応援したり、不満を示したりしたいから。

**Acceptance Criteria**

- 評価対象に対する衝動を選択できる。
- 文章によるレビューを必須にしない。
- 既存の感情表明の仕組みを継承する。

**TB-05：何度でも感情を表明する**

ユーザーとして、同じ対象に対して繰り返し感情を表明したい。

自分の感情の強さを表現するため。

**Acceptance Criteria**

- 既存の投票ルールを基本として、繰り返し表明できる。
- レア演出のON/OFFを切り替えられる。
- 表明結果が対象の集計に反映される。

### Activity 4：結果を見る

**TB-06：対象ごとの感情集計を見る**

ユーザーとして、評価対象ごとの感情集計を見たい。

対象にどのような感情が集まっているか知るため。

**Acceptance Criteria**

- 評価対象ごとに集計結果が独立している。
- 集計結果が可視化される。
- 自分や他のユーザーの表明が結果に反映される。
- 表示数値は人数や支持率ではなく、既存の集計ルールに基づく表明量として扱う。

### Activity 5：再訪・共有する

**TB-07：対象ページを共有する**

ユーザーとして、評価対象のページを他の人に共有したい。

他の人にも感情を表明してもらうため。

**Acceptance Criteria**

- 評価対象ごとに共有可能なURLが存在する。
- 共有されたURLから対象ページにアクセスできる。
- アクセスしたユーザーも感情を表明できる。

**TB-08：対象ページを再訪する**

ユーザーとして、一度訪れた対象の状態を再び確認したい。

自分が関心を持つ対象に集まる感情の変化を見たいから。

**Acceptance Criteria**

- 同じURLから対象ページを再訪できる。
- 最新の集計結果を確認できる。
- 過去に自分が表明したかどうかに関係なく、ページを利用できる。

## 5.4 ToBeで実現する状態

- ユーザーはカテゴリを選択できる。
- 評価対象を自由記述で入力できる。
- 対象ごとにページを作成できる。
- 対象ページを共有できる。
- 誰でも対象ページに感情を表明できる。
- 繰り返し感情を表明できる。
- 対象ごとに感情が独立して集計される。
- 集計結果が可視化される。
- レア演出をON/OFFできる。
- オリジナル版は引き続き利用できる。

## 6. ToBeの設計上の制約

### 6.1 集計の位置づけ

本サービスは、一般的なレビューサービスや満足度調査サービスとは異なる。

- 一人一票による支持率の算出を目的としない。
- 同じユーザーによる繰り返しの感情表明を許容する。
- 表明数と参加者数を混同しない。
- 表示された結果を、評価対象全体の客観的な評価として扱わない。

### 6.2 評価対象の単位

評価対象はカテゴリと対象名によって指定する。

一つの評価対象の中に、細かな評価テーマを作成する仕組みは設けない。

例：

- 漫画「ワンピース」への感情表明ページは作成できる。
- そのページ内に、キャラクター別・エピソード別などの評価テーマを作成する機能は設けない。

### 6.3 感情表明の娯楽性

レア演出や繰り返しの表明を通じて、感情表明そのものを楽しめる体験を維持する。

一方で、演出が感情表明の動機や頻度に影響する可能性を考慮し、レア演出のON/OFFを可能にする。

### 6.4 利用者と評価対象の関係

本サービスは、評価を受け取る企業や組織が実施する公式アンケートを主目的としない。

**評価を表明したいユーザーが、自発的に参加するサービス**とする。

評価対象の運営者や所有者がサービスに参加することは、感情表明の前提条件としない。

## 7. 未決事項

以下は本USMでは決定しない。

### Step 1

- レア演出のON/OFF設定の初期値・保存方法（→ 決定済み：初期値 ON、端末の localStorage に保存）
- 函南町モードとオリジナル版での投票制限の具体的な管理方法（→ 決定済み：target × 衝動ごとに独立）
- 既存API・データモデルをどのように拡張するか（→ 決定済み：キーを足す）

### ToBe

- 同じ名称の評価対象が作成された場合の重複判定
- カテゴリごとの衝動の種類・文言
- レア演出の設定をユーザー単位・対象ページ単位のどちらで管理するか
- 作成された評価対象ページの管理方法
- 不適切な評価対象の作成や組織的な嫌がらせへの対策
- 対象ページの検索・発見方法

未決事項は、必要となる開発フェーズで個別に検討する。

### 決定済み（2026-11-15）

- ToBe のストーリー ID は `TB-xx` とする（オリジナル版 USM §9.2 の技術課題 `T-xx` と区別するため）。
- レア演出の ON/OFF（S1-05）はオリジナル版に効く。函南町版はレア演出を設けない（OFF 固定）。初期値 ON、端末の localStorage に保存する。
- 函南町版の衝動の順序は 一揆したい → 荷物をまとめたい → 骨を埋めたい。
- 開いたときは毎回オリジナル版から始める。
- 集計の分離は、既存のデータモデル・API に「評価対象（target）」のキーを足す方法で行う（ToBe でも対象のキーが増えるだけで成立する）。詳細は `docs/world-api-design.md` §8。
- 函南町版では投票者の位置情報を使わない（送らない・集計しない）。

## 8. 開発上の基本方針

1. オリジナル版の既存仕様を尊重する。
2. Step 1は函南町モードの追加に限定する。
3. Step 1でカテゴリ選択やページ払い出しのための汎用基盤を先行開発しない。
4. 既存の投票・集計ロジックを確認し、再利用できる部分を活用する。
5. 投票上限・集計期間・寄与度調整などの仕様を、承認なく変更しない。
6. デザインの詳細は作成済みモックを参照し、本USMとは分離して管理する。
7. Step 1の実装と検証が完了してから、ToBeに向けた次の開発範囲を決定する。
